# 墨签 InkPad 串口协议（v1）

> 适用固件：`firmware_usb/` FW 1.0.0
> 适用上位机：`inkpad/app/serial.js`
> 最后更新：2026-10-26（M1 实机验证通过）

---

## 一、物理层

- ESP32-C3 原生 USB CDC（`ARDUINO_USB_MODE=1` + `ARDUINO_USB_CDC_ON_BOOT=1`）
- Windows 下识别为 `USB 串行设备 (COMx)`，**VID_303A / PID_1001**
- 逻辑波特率 115200（USB CDC 实际不受波特率限制，写这个值只是习惯）
- 打开端口时 **DTR/RTS 必须置 false**，否则可能把芯片带进下载模式，
  表现为"连上了但命令没反应"

---

## 二、帧格式

```
ASCII 命令行，每行以 \n 结尾
二进制数据块紧随 FRAME 命令之后，按 1KB 分块传输，每块有 ACK
```

### 图像帧

| 项 | 值 |
|---|---|
| 尺寸 | 400 × 300 |
| 每像素 | 2 bit |
| 总长 | 30000 字节 |
| 排列 | 行优先，每字节 4 像素，高位在前 |
| 调色板 | `0=黑 1=白 2=黄 3=红`（本屏无黄，2 显示为红） |

---

## 三、命令

| 命令 | 回复 | 说明 |
|---|---|---|
| `PING` | `PONG <ver>` | 探活 |
| `INFO` | `INFO w= h= bpp= cal= drv= mode= crc= fw=` | 设备能力 |
| `FRAME <len> <crc32>` | `READY` → 见下节 | 开始传帧 |
| `SHOW [crc32]` | `SKIP` 或 `SHOWING` → `DONE <ms>` | 刷屏。crc 与上次相同则跳过 |
| `TEST` | `SHOWING` → `DONE <ms>` | 四段测试图 |
| `CAL <0-3>` | `OK cal=<n>` | 极性：bit0 反 B 平面，bit1 反 R 平面 |
| `DRV <ssd1619\|ssd1683\|uc8276>` | `OK drv= cal=` | 切驱动，会重置 cal 为默认值 |
| `MODE <usb\|wifi>` | `OK` / `ERR wifi-disabled` | 切通路（WiFi 在 M6 启用） |
| `CFG <ssid> <pass>` | `OK` / `ERR wifi-disabled` | 配网存 NVS |
| `BLANK` | `SHOWING` → `DONE <ms>` | 清成白屏 |
| `RESET` | `OK rebooting` | 重启 |

---

## 四、传帧流程（重点）

```
上位机                         设备
  │  FRAME 30000 <crc32>  ────→
  │                        ←────  READY
  │  [1024 字节]           ────→
  │                        ←────  ACK 1024
  │  [1024 字节]           ────→
  │                        ←────  ACK 2048
  │        … 共 30 块 …
  │  [304 字节]            ────→
  │                        ←────  ACK 30000
  │                        ←────  OK            （CRC 校验通过）
  │  SHOW <crc32>          ────→
  │                        ←────  SHOWING
  │                        ←────  DONE 13662    （约 13.7 秒）
```

### 为什么必须分块 ACK

**30000 字节不能一口气写。** 实测：主机 `write` 回调正常返回，
设备只收到 17~22KB，**两边都不报错**，然后永久等待。

试过但不够的方案：
- 加大设备 RX 缓冲（256 → 8192）：从 17K 提到 22K，仍会丢
- 分块写 4096 + `drain()`：同样只到 22K
- 一口气写 + 事后等 `OK`：直接卡死

**分块 ACK 是唯一稳定的办法。** 30 个来回只有几十毫秒，
相比 13.7 秒的物理刷屏时间可以忽略。

### 断流自愈

设备在 `RX_BINARY` 状态如果 **3 秒没有新字节**，会主动放弃这一帧并回
`ERR timeout <收到>/<需要>`，然后回到命令行模式。

没有这个机制的话，一次断流会让设备永久卡在收帧状态，
之后所有命令都被当成帧数据吞掉，只能拔线重插。

## 五、颜色极性（cal）

| cal | B 平面 (0x24) | R 平面 (0x26) | 备注 |
|---|---|---|---|
| 0 | 直发 | 直发 | SSD1683 / UC8276 默认 |
| **2** | **直发** | **取反** | **SSD1619 默认，实测四段图全对** |
| 1 | 取反 | 直发 | |
| 3 | 取反 | 取反 | 老 `epd42_weather` 用的就是这档，会导致白底变黑底 |

**历史修正**：`epd42_weather` 对两个平面都取反，很可能就是当年
"后端渲染白底、屏幕显示黑底"的真正原因。四段测试图验证全对的那版
（`epd42_test`）是 **B 直发 + R 取反**，即 cal=2。

校准方法：`TEST` 刷四段图，看是否是
**黑条 → 白底黑字 B → 红条 → 棋盘格**。不对就换一档 `CAL` 再刷。

## 六、已知的日志粘连问题

ESP-IDF 有些日志（`spiAttachMISO`、`nvs_get_str`）**不带换行**，
会把紧随其后的串口回复粘在同一行，上位机按行解析就会漏掉回复。

两头都做了防护：

- **固件**：每条回复前先打 `\r\n`；SPI 的 MISO 传占位脚 GPIO5 消掉那条警告
- **上位机**：`_dispatch()` 除了整行匹配，还会从第一个协议关键字处切开再匹配一次

---

## 七、时序实测

| 操作 | 耗时 |
|---|---|
| 传 30000 字节（30 块 ACK） | 约 100 ms |
| 全刷（含 init + refresh + poweroff） | **13.7 s** |
| 其中纯物理刷新 | 约 13.4 s（不可优化） |

断电阶段不等 BUSY：这块屏断电后 BUSY 一直挂高，等就是白等 5 秒。
优化前是 18.5 秒，优化后 13.7 秒。

## 八、WiFi 副通路（M6）

固件有两种编译环境：

| 环境 | 宏 | 体积 | 功能 |
|---|---|---|---|
| `esp32c3` | 无 | 274KB | 只有 USB 通路 |
| `esp32c3-wifi` | `ENABLE_WIFI=1` | 775KB | USB + WiFi + mDNS + HTTP + UDP 发现 |

```bash
pio run -e esp32c3-wifi -t upload --upload-port COM12
```

### 8.1 新增串口命令

| 命令 | 回复 | 说明 |
|---|---|---|
| `SCAN` | `SSID <名字> <rssi>` × N，然后 `SCANDONE <N>` | 扫描周围 2.4GHz 网络 |
| `WIFI <ssid>\|<密码>` | `WIFI OK <ip>` / `WIFI ERR` | 连接网络并开 HTTP 服务 |
| `CFG <ssid>\|<密码>` | `OK` | 存进 NVS（不立即连接） |
| `AP <ssid>\|<密码>` | `AP OK <ssid> <ip>` | 进入 SoftAP 配置模式 |
| `MODE usb\|wifi\|ap` | `OK mode=<x>` | 切换通路 |
| `WIFIINFO` | `WIFIINFO <0/1> <ip> <ssid>` | 查询连接状态 |

> ⚠ **SSID 含空格时必须用 `|` 分隔**。原来用空格分隔会把 `My Printer Direct 100`
> 截断成 `My`——这是实测踩到的坑（打印机热点这类名字常带空格）。
>
> ⚠ 解析顺序有讲究：`strtok` 是有状态的，必须**先取剩余整段**再从里面切，
> 否则整段会被前面的 `strtok` 吃掉。

### 8.2 SoftAP 配置模式

设备自己开热点，电脑连上就能推图（IP 固定 `192.168.4.1`）：

```
电脑右下角 WiFi → 连上 inkpad-XXXX → 应用里填 192.168.4.1 → 推送
```

`MODE ap` 会自动生成随机 SSID（`inkpad-<4位十六进制>`）和密码（`inkpad<4位数字>`），
通过串口打印出来。

**这条路的价值**：不依赖路由器设置。用户的路由器如果是访客网络（有客户端隔离）
或者只开 5GHz，设备根本看不到，SoftAP 模式绕开了这个问题。

### 8.3 HTTP 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/info` | `{"ip":"...","ssid":"..."}` |
| GET | `/ping` | `{"pong":1}` |
| POST | `/frame?crc=<crc32>` | body 是 30000 字节 2bpp，返回 `{"ok":1}` |
| POST | `/show?crc=<crc32>` | 触发刷屏 |

HTTP 服务是**自己手写的**，没用 `WebServer`——因为要收 30000 字节的二进制 body，
`WebServer` 对非表单 body 的处理不可控。

### 8.4 帧格式与 USB 完全一致

两条通路共用同一套 `handleFrame()` / `acceptFrame()`，都是 30000 字节 2bpp + CRC32。
**区别只有一个**：USB 通路因为 Windows USB CDC 会丢数据，必须 1KB 分块 + ACK；
HTTP 是 TCP 有重传，整块 POST 就行。

### 8.5 发现设备（三条路，按顺序试）

1. **mDNS**：设备广播 `inkpad.local`，电脑解析 `inkpad.local`
2. **UDP 广播探测**：电脑向 `255.255.255.255:45353` 广播 `INKPAD?`，
   设备回自己的 IP（mDNS 在 Windows 上不一定能解析 `.local`，这条是兜底）
3. **手动填 IP**：SoftAP 模式下固定是 `192.168.4.1`

### 8.6 刷屏前会断射频

墨水屏刷新时 WiFi 射频会干扰波形，所以 `/show` 的处理顺序是：

```
回复 HTTP → crc 校验/SKIP 判断 → 等 300ms → 关射频（HTTP/UDP/mDNS 一起停）
→ 刷屏（13.7s）→ 按原模式恢复（热点模式重开同一热点 / STA 模式重连路由器）
```

这跟老 `epd42_weather` 的做法一致。三个防护：

- **crc 对不上不刷**：推来的 crc 和手上帧对不上说明帧没收到，直接跳过（先判断再断射频）
- **重复帧跳过**：crc 与上次刷的相同则跳过，对齐 USB 通路的 `SKIP` 语义
- **按原模式恢复**：热点凭据（随机生成的）会存一份在内存里，
  断射频后原样重开同一个热点，电脑不用重连；STA 模式则用 NVS 里的账号重连

### 8.7 实测环境限制

在这台开发机上**无法验证设备与电脑之间的 WiFi 链路**：

- 电脑连的是访客网络（NetworkCategory=Public），
  这种网络通常有**客户端隔离**，同网段设备互相不可见
- 路由器很可能只给访客分了 5GHz/6GHz，而 ESP32 只支持 2.4GHz
- 设备扫描只看到 1 个网络（一台打印机的直连热点，-53dBm），
  看不到电脑所在的那个网
- 而且开发环境里 `netsh wlan` 完全无输出，**无法从命令行操作电脑的 WiFi**，
  所以没法让电脑连上设备的 SoftAP 来做端到端验证

**已验证的部分**：应用侧传输层用 `tools/mock-device.js` 完整验过
（`node tools/wifi-test.js`，11 项全过）；固件侧的命令、SoftAP 启动、
扫描都实机跑通了。

**需要人工补的一步**：在能操作 WiFi 的机器上，按 §8.2 连上 `inkpad-XXXX`，
然后在应用里填 `192.168.4.1` 点推送。
